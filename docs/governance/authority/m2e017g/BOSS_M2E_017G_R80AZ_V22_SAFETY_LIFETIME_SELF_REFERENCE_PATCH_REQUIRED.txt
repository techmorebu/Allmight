======================================================================
DECISIVE DEFECT — SAFETY_SURFACE_FINAL_LINE RESOLVES TO THE PROBE ITSELF
======================================================================

v22 computes:

  SF_FINAL_LINE=$(grep -n 'emit "SAFETY_SURFACE"' "$SELF_SRC" | head -1 | cut -d: -f1)

Exact source contains the searched text at TWO relevant locations:

  line 1250:
    the SF_FINAL_LINE grep command itself

  line 1271:
    the actual authoritative:
      emit "SAFETY_SURFACE" ...

Because the probe uses:

  head -1

it returns line 1250.

Therefore the reported dry-run:

  final=1250

does NOT identify the final SAFETY_SURFACE verdict.

It identifies the verifier source line that searches for that verdict.

This is a classic BUG-009 verifier self-reference / false-positive class:

  probe searches source
  probe text contains its own search target
  first-match logic selects the probe itself
  order predicate still passes
  false PASS becomes possible

Current:

  SAFETY_FAIL_LIFETIME_ORDER=INIT_BEFORE_D01_INCREMENT_BEFORE_FINAL_VERDICT

is therefore not proven.

Required:

  AND
  SAFETY_FAIL_LIFETIME_ORDER == PASS

Otherwise:
  NO

======================================================================
THIRD DEFECT — FINAL COUNT IS EMITTED BEFORE THE PROOF CAN FAIL
======================================================================

v22 currently emits:

  SAFETY_FAIL_FINAL_COUNT "$SAFETY_FAIL"

before it evaluates the lifetime proof failure and potentially increments:

  SAFETY_FAIL=$((SAFETY_FAIL+1))

Therefore, if the lifetime proof fails:

  packaged SAFETY_FAIL_FINAL_COUNT

can be stale by at least one relative to the value used by the final
SAFETY_SURFACE verdict.

That creates contradictory evidence.

Required:

  evaluate/gate the lifetime proof first
  increment SAFETY_FAIL if needed
  THEN emit SAFETY_FAIL_FINAL_COUNT
  THEN emit final SAFETY_SURFACE

The emitted final count must equal the count actually used by the final safety
verdict.
